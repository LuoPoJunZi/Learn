# 5.3 构建证明、OIDC 与不可变发布

普通 CI 能告诉维护者“检查通过了”，但软件使用者还会关心另一个问题：下载到的文件是否真的由这个仓库、这个工作流、这个提交构建出来？

GitHub Artifact Attestations 可以为二进制、压缩包或容器镜像生成可验证的构建来源声明。它使用工作流的短期 OIDC 身份申请签名证书，不需要把长期签名私钥保存在仓库 Secrets 中。

## 适合人群

- 已经会使用 GitHub Actions，准备发布压缩包或可执行文件的人
- 想理解 OIDC、Sigstore、SLSA 和软件供应链安全的新手
- 维护安装脚本、CLI、容器镜像或 Release 附件的人
- 希望用户能验证下载文件来源的人

## 学习目标

读完后，你应该能：

- 区分哈希、签名、构建证明和不可变发布
- 看懂 Artifact Attestation 工作流所需权限
- 为一个构建产物生成 SLSA provenance
- 使用 GitHub CLI 验证产物来源
- 判断什么时候应该启用不可变发布或固定 Action SHA

## 四个概念先分清

| 概念 | 回答的问题 | 单独使用的局限 |
| :--- | :--- | :--- |
| SHA-256 哈希 | 文件内容有没有变化 | 如果哈希和文件一起被替换，用户仍可能受骗 |
| 数字签名 | 谁对这份内容签过名 | 仍要管理签名身份和密钥信任 |
| 构建证明 | 文件由哪个仓库、提交和工作流构建 | 只有实际验证证明时才产生安全价值 |
| 不可变发布 | 发布后的标签和附件能否再被替换 | 不能证明发布前的构建过程一定正确 |

这些能力互相补充。构建证明不是杀毒软件，也不会检查源码是否有后门；它主要提供“来源和构建过程可验证”这条信任链。

## 工作流程

```text
Git 提交
  -> GitHub Actions 构建文件
  -> 计算文件摘要
  -> 工作流通过 OIDC 证明自己的身份
  -> Sigstore 签发短期证书
  -> GitHub 保存构建证明
  -> 用户下载文件并执行 gh attestation verify
```

OIDC Token 是短期工作流身份，不是可以长期使用的云平台密码。`id-token: write` 允许当前 Job 请求这个 Token，但不会自动赋予仓库内容或云资源写权限；真正能做什么仍由 GitHub 权限和外部信任策略决定。

## 教学工作流

本仓库提供模板：

- [attested-release.yml](../../examples/attested-release.yml)

模板使用手动触发，把 `README.md` 和 `docs/` 打包成一个内容固定的 `tar.gz`，然后为这个文件生成证明并上传原文件。

要让它真正运行，需要把模板复制到仓库根目录：

```text
.github/
└── workflows/
    └── attested-release.yml
```

教学模板不会自动创建 GitHub Release，也不会在每次 push 时发布文件。这能避免新手在还没理解发布权限时意外制造公开版本。

## 为什么要设置这些权限

模板在 Job 内声明：

```yaml
permissions:
  contents: read
  id-token: write
  attestations: write
  artifact-metadata: write
```

- `contents: read`：读取仓库源码。
- `id-token: write`：请求短期 OIDC Token，用于获得签名身份。
- `attestations: write`：把证明写入 GitHub Attestations API。
- `artifact-metadata: write`：创建与产物关联的元数据记录。

不要为了省事写 `write-all`。权限应放在真正需要生成证明的 Job 上，普通测试 Job 继续只使用读取权限。

## 生成构建证明

核心步骤只有两部分：先构建一个明确的文件，再把同一个路径交给 `actions/attest`。

```yaml
- name: Generate build provenance
  uses: actions/attest@v4
  with:
    subject-path: dist/learn-docs.tar.gz
```

没有提供 SBOM 或自定义 predicate 时，`actions/attest` 会生成 SLSA build provenance。证明会把产物摘要与工作流身份关联起来。

当前 GitHub 官方说明：公开仓库可在现有 GitHub 计划中使用 Artifact Attestations；私有或内部仓库需要 GitHub Enterprise Cloud，GitHub Enterprise Server 不支持该功能。实际使用前仍应检查账号和平台的最新可用范围。

## 为什么直接上传原文件

模板使用 `actions/upload-artifact@v7` 的直接上传模式：

```yaml
- name: Upload the exact attested file
  uses: actions/upload-artifact@v7
  with:
    path: dist/learn-docs.tar.gz
    archive: false
```

如果上传工具再次把文件包进另一个 ZIP，用户下载后要先解包才能取得被证明的原始文件。直接上传可以让下载文件与 `subject-path` 指向的文件保持一致，也保留 `tar.gz` 自身的权限和文件名语义。

这是较新的 `upload-artifact` 能力。自托管 Runner 使用前要确认 Runner 版本满足该 Action 要求；GitHub Enterprise Server 也有不同的 Artifact Action 兼容限制。

## 在 GitHub 页面运行

1. 提交工作流到 `.github/workflows/`。
2. 打开仓库的 **Actions** 页面。
3. 选择 **Build and attest release artifact**。
4. 点击 **Run workflow**。
5. 等待 `package` Job 完成。
6. 在运行摘要中下载 `learn-docs.tar.gz`。

失败时先点开具体 Step。权限不足通常会出现在 OIDC 或写入证明阶段；路径错误通常会出现在打包、证明或上传阶段。

## 验证下载文件

先安装并登录较新的 GitHub CLI，然后在文件所在目录运行：

```bash
gh attestation verify learn-docs.tar.gz --repo OWNER/REPOSITORY
```

把 `OWNER/REPOSITORY` 替换为真实仓库，例如 `octo-org/example`。验证成功表示：

- 文件摘要与证明中的 subject 一致。
- 证明签名链有效。
- 证明与指定 GitHub 仓库关联。

验证失败时不要继续运行文件。先确认是否下载错版本、仓库名是否正确、文件是否被浏览器或传输工具改动，再查看发布者说明。

GitHub CLI 还支持下载证明和可信根后进行离线验证。离线场景需要同时安全传递产物、证明 bundle 和可信根，并定期更新可信根信息。

## 容器镜像有什么不同

容器镜像通常使用镜像名称和 digest，而不是本地文件路径：

```yaml
- name: Attest container image
  uses: actions/attest@v4
  with:
    subject-name: ghcr.io/OWNER/IMAGE
    subject-digest: ${{ steps.push.outputs.digest }}
    push-to-registry: true
```

`subject-name` 不要包含 `:latest` 之类标签，`subject-digest` 应来自实际 push 步骤。镜像发布还需要 `packages: write` 和容器仓库登录，不应直接把上面片段粘进普通文档项目。

## 不可变发布解决什么问题

GitHub 的 Immutable Releases 会锁定已经发布的 Release 标签和附件，防止它们在发布后被悄悄替换。GitHub 还会为不可变发布自动生成 Release Attestation。

启用后应采用“先草稿、后发布”的流程：

1. 创建 Draft Release。
2. 上传并检查全部附件。
3. 核对标签、版本说明和校验信息。
4. 确认不再修改后发布。

一旦发布成为不可变版本，不能再像普通 Release 那样随意替换附件或移动标签。它适合正式版本，不适合仍在频繁调整的临时文件。

## 固定 Action 版本

教学模板使用 `@v6`、`@v4` 和 `@v7` 主版本标签，便于阅读和获取兼容更新。但标签理论上可以移动，高安全发布工作流可固定到经过核验的完整 Commit SHA：

```yaml
- uses: actions/attest@完整的四十位提交SHA
```

固定 SHA 后不会自动获得安全修复，因此还要使用 Dependabot 或定期审查更新。不要固定到来源不明 Fork 的 SHA，也不要使用缩写 SHA。

## 常见错误

### 只生成证明，从来不验证

GitHub 官方特别强调，生成证明本身不自动带来安全收益。发布说明应告诉用户具体的验证命令。

### 证明的是一个文件，发布的是另一个文件

压缩、重命名或重新打包都会改变摘要。证明步骤和上传步骤必须指向同一最终产物。

### 给整个工作流开放写权限

只给生成证明的 Job 最小权限。测试第三方代码的 Job 不应顺便获得发布权限。

### 把 OIDC 当成普通 API Token

OIDC 是短期身份交换机制。不要尝试把 OIDC Token 保存成长期 Secret，也不要把它打印进日志。

### 发布后还打算替换附件

启用不可变发布前先调整流程：所有附件在 Draft 阶段准备完整，发布后通过新版本修复，而不是覆盖旧版本。

## 完成检查清单

- [ ] 构建产物在证明前已经最终定型
- [ ] Job 只拥有所需的最小权限
- [ ] 证明和上传指向同一个文件或 digest
- [ ] 已在另一台环境执行 `gh attestation verify`
- [ ] 发布说明写明仓库名和验证命令
- [ ] 第三方 Action 使用可信来源和明确版本
- [ ] 正式 Release 在发布前经过 Draft 检查
