# 5.4 可复用工作流与 Dependabot 分组升级

在团队管理多个 GitHub 仓库或随着单一项目规模扩大时，开发者常常陷入两类经典维护困境：
1. **YAML 复制粘贴噩梦**：每个仓库都要维护一套几乎完全一致的代码质检（Linting）、多系统矩阵测试（Matrix Test）和 Docker 打包流水线；一旦规范更新，必须逐个仓库提交 PR。
2. **Dependabot PR 轰炸**：开启依赖自动检测后，每一个次要依赖的小版本更新都会单独触发一个 PR，几十个未合并的 PR 让代码仓库列表混乱不堪。

GitHub Actions 提供的**可复用工作流（Reusable Workflows）**和 Dependabot 的**分组升级规则（Grouped Updates）**，正是解决这两大痛点的现代化工程标准。

---

## 适合人群

- 已经在项目中配置过基础 GitHub Actions CI，希望消除重复 YAML 的维护者。
- 维护多个类似微服务或库仓库，追求规范统一的工程团队。
- 受够了 Dependabot 每日“单包单 PR”通知轰炸的开源开发者。

## 学习目标

完成本章后，你应该能够：

- 清晰区分**可复用工作流 (`workflow_call`)** 与 **复合 Action (Composite Action)** 的定位与边界。
- 独立编写包含输入（`inputs`）、密钥（`secrets`）和产出（`outputs`）的标准化可复用流水线。
- 在主工作流中优雅调用可复用工作流，并结合版本矩阵（Matrix Strategy）实现跨平台自动化测试。
- 配置 `dependabot.yml` 的 `groups` 属性，将零散依赖聚合为单次升级 PR，并配合自动合并策略。

---

## 架构模型：调用方与被调用方

```text
[调用方工作流 (Caller)]                       [可复用工作流 (Reusable)]
.github/workflows/main-ci.yml                 .github/workflows/shared-test.yml
  job: call-test                                on:
    uses: ./.github/workflows/shared-test.yml     workflow_call:
    with:                                           inputs:
      python-version: "3.12"                          python-version: ...
    secrets:                                        secrets:
      token: ${{ secrets.DEPLOY_TOKEN }}              token: ...
                                                jobs:
                                                  run-check:
                                                    runs-on: ubuntu-latest
                                                    steps: ...
```

---

## 机制选型：可复用工作流 vs 复合 Action

| 特性维度 | 可复用工作流 (Reusable Workflow) | 复合 Action (Composite Action) |
| :--- | :--- | :--- |
| **触发器声明** | `on: workflow_call` | `runs: using: "composite"` |
| **复用粒度** | **整个 Job 级别**（包含独立运行器分配） | **单一 Step 步骤级别**（嵌入当前已有 Job 中） |
| **多任务调度** | 支持直接定义多个并行 Job 或矩阵 | 仅能在单个 Job 内部执行一系列顺序 Steps |
| **密钥传递** | 严格显式传递（或 `secrets: inherit`） | 默认直接继承外层 Job 的当前环境权限 |
| **典型场景** | 标准化全套 CI/CD 质检与发布流程 | 封装多行重复 Shell 脚本或环境初始化动作 |

## 第一步：编写可复用工作流定义

在仓库中创建 `.github/workflows/reusable-python-ci.yml`：

本模板面向包含 `tests/test_*.py` 的 Python 项目；请先准备至少一个真实测试。当前学习仓库的数值回归测试位于 `scripts/tests`，套用模板时应把下面的 `-s tests` 改为 `-s scripts/tests`。本仓库实际运行的 CI 仍以 [统一检查工作流](5.2-github-actions-ci.md) 为准。

```yaml
name: Shared Python CI Pipeline

on:
  workflow_call:
    inputs:
      python-version:
        description: "运行测试的 Python 版本"
        required: false
        default: "3.12"
        type: string
      run-coverage:
        description: "是否开启代码覆盖率统计"
        required: false
        default: false
        type: boolean
    secrets:
      API_TOKEN:
        description: "部署或第三方上报使用的密钥凭据"
        required: false
    outputs:
      python-version:
        description: "实际使用的解释器版本"
        value: ${{ jobs.lint-and-test.outputs.python-version }}

jobs:
  lint-and-test:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    outputs:
      python-version: ${{ steps.runtime.outputs.version }}
    steps:
      - name: 检出源码
        uses: actions/checkout@v4

      - name: 设置 Python 运行环境
        uses: actions/setup-python@v5
        with:
          python-version: ${{ inputs.python-version }}

      - name: 记录解释器版本
        id: runtime
        run: echo "version=$(python --version)" >> "$GITHUB_OUTPUT"

      - name: 安装基础依赖
        run: |
          python -m pip install --upgrade pip
          if [ -f requirements.txt ]; then pip install -r requirements.txt; fi

      - name: 运行语法与代码质量检查
        run: |
          python -m compileall -q .

      - name: 运行单元测试
        if: ${{ !inputs.run-coverage }}
        run: python -m unittest discover -s tests -p 'test_*.py'

      - name: 条件执行覆盖率分析
        if: ${{ inputs.run-coverage }}
        run: |
          python -m pip install coverage
          python -m coverage run -m unittest discover -s tests -p 'test_*.py'
          python -m coverage report
          python -m coverage xml
```

本例没有无条件开启 `setup-python` 的 pip 缓存：学习仓库没有根目录依赖清单，直接启用可能因找不到哈希文件失败。真实项目可在存在依赖清单时配置 `cache: pip` 与正确的 `cache-dependency-path`。覆盖率步骤会真正运行测试并生成 `coverage.xml`；可选 `API_TOKEN` 仅演示声明和传递，不会被本例上传到第三方服务。

## 第二步：在主工作流中调用

在日常触发的 `.github/workflows/ci.yml` 中调用上述可复用模板：

```yaml
name: Main Repository CI

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  # 矩阵式调用可复用工作流
  matrix-checks:
    strategy:
      matrix:
        py_ver: ["3.10", "3.11", "3.12"]
    uses: ./.github/workflows/reusable-python-ci.yml
    with:
      python-version: ${{ matrix.py_ver }}
      run-coverage: ${{ matrix.py_ver == '3.12' }}
    secrets:
      API_TOKEN: ${{ secrets.SHARED_REPORTER_TOKEN }}
```

> [!TIP]
> **跨仓库共享**：如果该模板放在公共规范仓库中（如 `my-org/shared-workflows`），只需把 `uses:` 修改为 `my-org/shared-workflows/.github/workflows/shared.yml@v1`。**强烈推荐使用明确的 Git Tag 或 Commit SHA 锁定版本**，防止公共仓库被恶意篡改引入供应链攻击。

## 第三步：Dependabot 分组升级实战

在仓库根目录下创建或编辑 `.github/dependabot.yml`，通过 `groups` 特性将同类零碎更新收敛至单一 PR：

```yaml
version: 2
updates:
  # 1. 自动追踪管理 GitHub Actions 自身插件版本
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"
    groups:
      actions-dependencies:
        patterns:
          - "*" # 将所有 actions 升级聚合进一个每周 PR

  # 2. 自动追踪 Python / pip 依赖
  - package-ecosystem: "pip"
    directory: "/"
    schedule:
      interval: "weekly"
    groups:
      # 单元测试与代码格式化工具组 (低风险聚合)
      dev-dependencies:
        patterns:
          - "pytest*"
          - "flake8*"
          - "black"
          - "ruff"
      # 核心生产运行时依赖组
      core-dependencies:
        patterns:
          - "flask*"
          - "fastapi*"
          - "pydantic*"
```

### 效果前后对比

- **配置前**：`pytest`、`flake8`、`black` 每周各自发起一个 PR，单周产生 3~5 个 PR 并触发重复 CI 消耗额度。
- **配置后**：Dependabot 统一发起一个名为 `build(deps): bump dev-dependencies in the pip group` 的聚合 PR，一次合并所有测试工具补丁。

## 安全提醒与最小权限

1. **不可信 PR 防范**：在处理来自 Fork 仓库的外部 PR 时，可复用工作流**不要无条件授予 `write` 写入权限**；坚持 `permissions: contents: read` 原则。
2. **谨慎使用 `secrets: inherit`**：虽然 `inherit` 能快速将所有密钥直接透传给子工作流，但若被调用的工作流由外部或第三方维护，可能导致仓库敏感 Token 泄露。始终推荐按需显式传递单个密钥。

## 常见错误与排查

### 1. 报错 `workflow_call is not a valid event`
- **原因**：可复用工作流必须被放置在仓库的 `.github/workflows/` 顶层目录下，若放置在子目录（如 `.github/workflows/nested/`）GitHub Actions 将无法识别。

### 2. 报错 `secrets cannot be read`
- **原因**：调用方没有显式定义 `secrets:` 节点，或者在组织（Organization）设置中未授权被调用仓库访问该 Secret。

## 少量自查

1. **如果只需要在已有 Job 的其中一步复用安装环境脚本，应该选用可复用工作流还是复合 Action？**
   - *参考答案*：选用复合 Action（Composite Action），因为复合 Action 是 Step 粒度的，无需分配全新运行器，执行开销更小。
2. **Dependabot 配置中的 `patterns: ["*"]` 会带来什么效果？**
   - *参考答案*：对该更新配置中匹配的版本更新分组。安全更新、不同目录或不同更新配置可能仍产生独立 PR，不保证整个仓库每周只有一个 PR。
3. **调用外部公共仓库的可复用工作流时，引用方式写成 `@main` 存在什么安全隐患？**
   - *参考答案*：`@main` 指向浮动分支，若上游分支被黑客入侵注入恶意步骤，下游仓库执行时将直接受害；应使用固定版本 Tag（如 `@v1.2.0`）或完整的 40 位 Commit SHA 锁定。
