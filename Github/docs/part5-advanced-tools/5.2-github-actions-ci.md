# 5.2 用 GitHub Actions 自动检查代码

当你每次提交代码后都要手动运行相同检查，很容易忘记其中一步。GitHub Actions 可以在代码推送或 Pull Request 创建时，自动准备一台临时运行器并执行检查命令。

这类流程通常叫 Continuous Integration，简称 CI，也就是“持续集成”。

## 适合人群

- 已经会提交和推送代码的新手。
- 想让 Pull Request 自动显示“检查通过”或“检查失败”的维护者。
- 想学习 YAML、工作流、Job 和 Step 基础概念的人。

## 学习目标

- 知道工作流文件应该放在哪里。
- 看懂 `on`、`permissions`、`jobs`、`steps` 和 `uses`。
- 使用版本矩阵检查多个 Python 版本。
- 理解最小权限、超时和取消重复任务为什么重要。
- 能把本仓库示例改成自己项目的 CI。

## 工作流放在哪里

真正会被 GitHub 自动执行的工作流必须放在仓库根目录下：

```text
.github/
└── workflows/
    └── quality.yml
```

本教程提供的模板位于：

- [Github/examples/python-quality.yml](../../examples/python-quality.yml)

它放在 `examples` 中时只是一份教学文件，不会自动运行。确认内容适合自己的项目后，再把它放进根目录的 `.github/workflows/`。

## 先看完整流程

```text
push 或 Pull Request
  -> GitHub 创建临时运行器
  -> 拉取仓库代码
  -> 安装指定 Python 版本
  -> 编译 Python 文件
  -> 运行代码检查
  -> 运行文档检查
  -> 在提交和 PR 页面显示结果
```

## 逐段理解模板

### 1. 工作流名称

```yaml
name: Python quality checks
```

这个名称会显示在 GitHub 的 Actions 页面和 Pull Request 检查列表中。名称应该让人一眼看出它在检查什么。

### 2. 触发条件

```yaml
on:
  push:
    branches: [main]
  pull_request:
```

含义是：

- 有代码推送到 `main` 时运行。
- 创建或更新 Pull Request 时运行。

刚开始学习时，不建议立刻加入定时任务或自动发布。先把“提交后自动检查”跑通。

### 3. 最小权限

```yaml
permissions:
  contents: read
```

检查代码只需要读取仓库，所以不给写入权限。最小权限可以减少工作流或第三方 Action 被滥用时的影响范围。

当任务确实需要创建 Release、发布包或写评论时，再为对应 Job 增加具体权限。

### 4. 取消重复运行

```yaml
concurrency:
  group: quality-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

如果你连续向同一个分支推送三次，前两次检查结果通常已经没有意义。`concurrency` 会取消旧运行，只保留最新一次，节省等待时间和运行额度。

### 5. Job 与运行器

```yaml
jobs:
  check:
    runs-on: windows-latest
    timeout-minutes: 10
```

- `check` 是 Job 的内部名称。
- `windows-latest` 表示使用 GitHub 托管的 Windows 运行器。
- `timeout-minutes` 防止命令卡住后一直占用资源。

本仓库的维护命令使用 PowerShell，因此示例选择 Windows。普通 Python 项目也可以使用 `ubuntu-latest`。

### 6. Python 版本矩阵

```yaml
strategy:
  fail-fast: false
  matrix:
    python-version: ["3.11", "3.13"]
```

GitHub 会分别创建 Python 3.11 和 3.13 两个检查任务。这样可以发现“在我的版本能运行，在另一个版本报错”的兼容性问题。

`fail-fast: false` 表示一个版本失败时，另一个版本仍然继续，方便一次看到完整结果。

### 7. Step 与 Action

```yaml
steps:
  - name: Check out repository
    uses: actions/checkout@v6

  - name: Set up Python
    uses: actions/setup-python@v6
    with:
      python-version: ${{ matrix.python-version }}
```

- `uses` 调用已经写好的 Action。
- `with` 向 Action 传入参数。
- `${{ matrix.python-version }}` 会读取当前矩阵任务的 Python 版本。

`checkout` 和 `setup-python` 都来自 GitHub 官方维护的 `actions` 组织。

### 8. 执行项目命令

```yaml
- name: Compile Python files
  run: python -m compileall -q Python scripts

- name: Run repository code checks
  shell: pwsh
  run: ./scripts/check-code.ps1
```

`run` 后面就是你平时在终端里执行的命令。CI 最理想的状态是“本地和 GitHub 使用同一套检查命令”，避免两边标准不同。

## 如何用于自己的项目

1. 在仓库根目录创建 `.github/workflows/`。
2. 把示例内容保存为 `quality.yml`。
3. 根据项目修改 Python 版本和检查命令。
4. 提交并推送文件。
5. 打开 GitHub 仓库的 **Actions** 页面查看运行状态。
6. 如果失败，点进失败的 Step 阅读日志，而不是反复盲目重跑。

例如，使用 pytest 的项目可以把检查命令改成：

```yaml
- name: Install test dependencies
  run: python -m pip install -r requirements.txt

- name: Run tests
  run: python -m pytest
```

## 安全提醒

### 不要直接运行不可信代码并暴露密钥

来自外部贡献者的 Pull Request 可能包含恶意代码。不要在会运行 PR 代码的任务中随意提供部署密钥、云服务 Token 或生产密码。

### 谨慎使用 `pull_request_target`

`pull_request_target` 在目标仓库上下文中运行，权限和 Secrets 行为与普通 `pull_request` 不同。新手应优先使用普通 `pull_request`，除非已经理解安全边界。

### 审查第三方 Action

- 优先使用可信维护者提供的 Action。
- 查看仓库、发布记录和许可证。
- 版本标签便于阅读，但标签可能移动；高安全环境可固定到完整 Commit SHA。
- 使用 Dependabot 等工具跟踪 Action 更新，而不是长期停在过期版本。

## 常见错误

### 工作流完全没有运行

检查文件是否真的位于根目录的 `.github/workflows/`，扩展名是否为 `.yml` 或 `.yaml`，触发分支是否写对。

### YAML 缩进错误

YAML 依赖缩进表达层级。统一使用空格，不要混用 Tab。冒号后通常需要一个空格。

### 本地通过，CI 失败

重点比较：

- Python 版本是否相同。
- 是否漏装依赖。
- 文件名大小写是否一致。
- 是否依赖本机才有的路径、环境变量或软件。
- 测试是否偷偷依赖已有缓存或本地数据。

### Action 版本不可用

打开对应 Action 的官方仓库检查当前主版本及运行器要求，再更新 `uses`。不要凭印象随意猜版本号。

## 少量自查

1. 为什么代码检查通常只需要 `contents: read`？
2. 为什么同一分支连续推送时可以取消旧检查？
3. `uses` 和 `run` 的区别是什么？

参考答案：

1. 因为检查只读取代码，不需要修改仓库内容。
2. 旧提交已经被新提交替代，继续检查通常只会浪费时间和额度。
3. `uses` 调用已有 Action，`run` 执行运行器中的终端命令。
