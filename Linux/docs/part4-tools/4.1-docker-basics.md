# 4.1 Docker 容器极简入门

在软件开发中，最令人沮丧的报错之一莫过于：“这套程序在我电脑上明明运行正常，为什么部署到服务器上就报错了？”

传统的解决方式是整机导出虚拟机（VM），但虚拟机自带完整的客户机操作系统内核，体积动辄数十 GB，启动缓慢且极耗内存。**Docker 容器技术**通过共享宿主机 Linux 内核，并借助 Linux 的**命名空间（Namespaces）**和**控制组（Cgroups）**实现轻量级进程隔离，使得应用及其完整运行环境能够被打包成几 MB 至几十 MB 的标准镜像，在任何支持容器的机器上秒级启动。

---

## 适合人群

- 经常为 Python / Node.js 等运行环境版本冲突、依赖缺失而困扰的开发者。
- 准备将本地应用部署到 VPS 服务器，希望实现一键迁移与启动的运维新手。
- 听说过 Docker，但不清楚“镜像、容器、卷、Compose”彼此关系的学习者。

## 学习目标

完成本章后，你应该能够：

- 清晰辨析虚拟机与容器、镜像（Image）与容器（Container）的本质区别。
- 掌握 Docker 核心命令（`pull`、`run`、`ps`、`stop`、`logs`、`exec`）。
- 独立编写包含最佳层缓存实践与多阶段构建（Multi-stage Build）的标准 `Dockerfile`。
- 理解 Bind Mount（目录挂载）与 Docker Volume（持久化卷）的选型差异。
- 使用 `docker compose` 编排一个包含 Web 服务和 Redis 缓存的双容器环境。

## 先建立核心概念模型

### 1. 镜像 vs 容器

```text
  [Dockerfile]  --- 构建 build --->  [Docker 镜像 Image]  --- 运行 run --->  [运行中容器 Container]
(源码/构建配方)                      (只读只分发的模板蓝图)                    (具有隔离文件系统的活进程)
                                 (类似面向对象中的 Class)                  (类似面向对象中的 Instance)
```

- **镜像 (Image)**：只读的层级文件系统包，打包了应用程序及其所有依赖库和系统工具。
- **容器 (Container)**：镜像运行时的独立进程实例，在只读镜像层上方叠加了一层可写层。

### 2. 容器与虚拟机的底层对比

```text
+-----------------------+       +-----------------------+
|  应用 A  |   应用 B    |       |  应用 A  |   应用 B    |
+-----------------------+       +----------+------------+
|  依赖库  |   依赖库    |       | 客户机 OS| 客户机 OS  |
+-----------------------+       +----------+------------+
| Docker 引擎 (Namespace)|       |  Hypervisor (虚拟化层) |
+-----------------------+       +-----------------------+
| 宿主机 Linux 操作系统内核 |       | 宿主机操作系统 / 硬件  |
+-----------------------+       +-----------------------+
       [容器架构]                       [传统虚拟机]
```

## 第一步：安装与验证

下面用于原生 Ubuntu / Debian。已有容器服务的机器先核对当前安装方式与数据备份，再按官方安装页处理冲突包；不要直接卸载正在使用的 Docker 或 containerd。

```bash
# 确认发行版；Ubuntu 与 Debian 必须使用各自的软件源
. /etc/os-release
case "$ID" in
    ubuntu|debian) DOCKER_DISTRO="$ID" ;;
    *) echo "请改用该发行版的 Docker 官方安装说明"; exit 1 ;;
esac

# 安装基础证书与工具
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg

# 添加 Docker 官方 GPG 密钥
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL "https://download.docker.com/linux/$DOCKER_DISTRO/gpg" | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

# 设置软件源仓库
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/$DOCKER_DISTRO $VERSION_CODENAME stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

# 安装 Docker 引擎及 Compose 插件
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# 验证运行（免 root 用户配置见后文安全提醒）
sudo docker run hello-world
```

若看到 `Hello from Docker! This message shows that your installation appears to be working correctly.` 即代表安装成功。

## 第二步：容器日常高频操作

```bash
# 1. 从官方镜像中心拉取轻量镜像
docker pull python:3.12-slim

# 2. 交互式启动一个容器并进入终端（--rm 表示退出时自动清理容器）
docker run -it --rm python:3.12-slim bash

# 3. 后台运行一个 Nginx 容器，并将宿主机 8080 端口映射到容器内 80 端口
docker run -d --name my-web -p 127.0.0.1:8080:80 nginx:alpine

# 4. 查看当前正在运行的容器
docker ps

# 5. 查看所有容器（包含已停止退出的容器）
docker ps -a

# 6. 实时追踪查看容器内部日志
docker logs -f my-web

# 7. 进入正在运行中的容器内部执行诊断排查
docker exec -it my-web sh

# 8. 停止与删除容器
docker stop my-web
docker rm my-web
```

## 第三步：手写标准 Dockerfile 与层缓存优化

假设我们有一个简单的 Python 自动化脚本或小型 API 项目，目录结构如下：

```text
my-project/
├── app.py
├── requirements.txt
├── Dockerfile
└── .dockerignore
```

为了让后面的 Compose 示例可运行，`requirements.txt` 写入 `redis>=5,<8`，`app.py` 使用下面的最小访问计数服务。容器在 `0.0.0.0:8000` 监听，宿主机通过端口映射控制可访问范围：

```python
import os
from http.server import BaseHTTPRequestHandler, HTTPServer

import redis

cache = redis.Redis(
    host=os.environ.get("REDIS_HOST", "127.0.0.1"),
    socket_timeout=2,
    socket_connect_timeout=2,
)


class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        try:
            body = f"Visits: {cache.incr('visits')}\n".encode("utf-8")
            self.send_response(200)
        except redis.RedisError:
            body = b"Cache unavailable\n"
            self.send_response(503)
        self.send_header("Content-Type", "text/plain; charset=utf-8")
        self.end_headers()
        self.wfile.write(body)


if __name__ == "__main__":
    HTTPServer(("0.0.0.0", 8000), Handler).serve_forever()
```

在 `.dockerignore` 中排除 `.git/`、`.env`、`.venv/` 和 `__pycache__/`，避免 `COPY . .` 把凭据与本地环境打进镜像。

### 非 root 用户与多阶段构建范例

```dockerfile
# 1. 选用明确版本号的轻量基础镜像（不要使用 latest）
FROM python:3.12-slim AS builder
WORKDIR /build
COPY requirements.txt .
RUN pip wheel --no-cache-dir --wheel-dir /wheels -r requirements.txt

FROM python:3.12-slim

# 2. 设置容器内部工作目录
WORKDIR /app

# 3. 设置非交互与 Python 无缓冲标准输出环境变量
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

# 4. 关键技巧：先单独复制依赖文件，充分利用 Docker 层缓存 (Layer Caching)
COPY requirements.txt .

# 5. 只从构建阶段复制依赖包；最终镜像不保留构建环境
COPY --from=builder /wheels /wheels
RUN pip install --no-cache-dir --no-index --find-links=/wheels -r requirements.txt

# 6. 复制其余源代码（由于业务代码变动频繁，放在底层避免破坏 pip 安装层缓存）
COPY . .

# 7. 创建非 root 安全运行用户
RUN useradd -m -u 1000 appuser && chown -R appuser:appuser /app
USER appuser

# 8. 声明暴露端口（文档性指引，实际端口映射由 run 参数决定）
EXPOSE 8000

# 9. 容器启动入口命令
CMD ["python", "app.py"]
```

#### 构建与测试运行

```bash
# 构建镜像并打标签（-t 指定镜像名:版本号）
docker build -t my-python-app:1.0 .

# 在后台启动容器
docker run -d --name app-instance -p 127.0.0.1:8000:8000 my-python-app:1.0
```

单独启动 Web 服务而没有 Redis 时，请求返回 503；完成下方 Compose 配置后才会产生计数。双阶段构建展示依赖与运行环境分离，不保证所有项目的最终镜像都更小。

## 第四步：数据持久化——Volume 与 Bind Mount

容器的可写层具有临时性，容器一旦被删除，其内部生成的数据也会丢失。为保证数据安全，Docker 提供了两种主要持久化方案：

```text
+---------------------+           +---------------------+
|    Bind Mount       |           |    Named Volume     |
| (适合本地代码实时热重载)|           | (适合数据库/生产持久存储) |
+---------------------+           +---------------------+
| 宿主机指定任意物理绝对路径|           | 由 Docker 引擎在内部集中管理|
| 例如: /home/user/app|           | 路径: /var/lib/docker/..|
+---------------------+           +---------------------+
```

### 命令实操

```bash
# 方案 A: Bind Mount (本地开发时挂载代码目录，改代码免重新 build)
docker run -d -p 127.0.0.1:8000:8000 -v "$(pwd):/app" my-python-app:1.0

# 方案 B: Named Volume (生产环境数据库持久化)
docker volume create db_data
docker run -d --name redis-server -v db_data:/data redis:alpine redis-server --appendonly yes
```

## 第五步：多容器编排实战——Docker Compose

当应用逐渐演进为“Web 服务 + Redis 缓存 + PostgreSQL 数据库”等多组件结构时，逐个敲 `docker run` 并手动配置网络极易遗漏参数。

通过项目根目录下的 `compose.yaml` 文件，可以一键协同管理多容器：

```yaml
services:
  web:
    build: .
    ports:
      - "127.0.0.1:8000:8000"
    environment:
      - REDIS_HOST=cache
    depends_on:
      cache:
        condition: service_healthy
    restart: unless-stopped

  cache:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5
    volumes:
      - redis_data:/data
    restart: unless-stopped

volumes:
  redis_data:
```

### Compose 常用运维指令

```bash
# 后台一键构建并拉起整个服务集群
docker compose up -d

# 查看集群各服务运行状态
docker compose ps

# 聚合查看所有服务的实时联合日志
docker compose logs -f

# 停止并清理集群网络与容器（默认保留持久化 volume）
docker compose down
```

只有需要清空练习数据时才执行下面的命令；`-v` 会删除 Compose 管理的数据卷，计数和数据库内容会丢失，执行前确认备份：

```bash
docker compose down -v
```

## 安全提醒与最佳实践

1. **优先使用非 root 用户运行 Web 服务**：`USER appuser` 可以减少权限，但容器共享内核，不能保证阻止逃逸；也不要向应用容器挂载 Docker socket 或授予特权模式。
2. **切勿把密码、API Key 硬编码进 Dockerfile**：使用环境变量（`docker run -e KEY=...`）或 Docker Secrets / `.env` 注入敏感凭据。
3. **给应用设定内存与 CPU 上限**：
   ```bash
   docker run -d --memory="512m" --cpus="1.0" my-app
   ```
   防止某一个失控的容器耗尽宿主机资源导致整台 VPS 死机。

## 常见错误与排查

### 1. 报错 `permission denied while trying to connect to the Docker daemon socket`
- **原因**：当前普通 Linux 用户未加入 `docker` 用户组，无权访问 `/var/run/docker.sock`。
- **解决**：
  加入 `docker` 组相当于获得宿主机 root 级控制能力，只对可信管理员使用；也可以逐次使用 `sudo docker`，或按官方说明采用 Rootless 模式。
  ```bash
  sudo usermod -aG docker $USER
  # 重新登入或执行以下命令刷新组权限
  newgrp docker
  ```

### 2. 容器刚刚启动便立即 Exit 退出
- **原因**：Docker 容器要求主进程（PID 1）必须在前台持续运行。如果执行的是 `CMD ["service", "nginx", "start"]` 这类默认退出到后台的守护命令，容器认为任务已结束便会自动关闭。
- **解决**：让进程在前台运行，例如 `nginx -g 'daemon off;'` 或 `python app.py`。

## 少量自查

1. **在编写 Dockerfile 时，为什么建议先执行 `COPY requirements.txt .` 并运行 `pip install`，然后再执行 `COPY . .`？**
   - *参考答案*：Docker 按指令逐层建立镜像缓存。依赖列表变动频率远低于业务代码，先安装依赖能最大化命中缓存，避免每次修改一行代码都要漫长重装全部依赖。
2. **Bind Mount 和 Named Volume 适用的主要场景分别是什么？**
   - *参考答案*：Bind Mount 适合本地开发调试代码热加载；Named Volume 由 Docker 托管性能更佳，且隔离宿主机直接误删风险，适合数据库和生产日志。
3. **`docker stop` 和 `docker kill` 的区别是什么？**
   - *参考答案*：`stop` 首先向进程发送 `SIGTERM` 信号给予时间保存数据并优雅退出（超时后再强杀）；`kill` 则直接发送 `SIGKILL` 立即强制终止。
