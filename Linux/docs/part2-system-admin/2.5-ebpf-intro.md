# 2.5 eBPF 内核观测入门

长期以来，排查 Linux 服务器出现的偶发性网络抖动、高延迟或者隐蔽的恶意后门程序是一件极其棘手的事情。传统工具如 `strace` 会暂停目标进程导致性能雪崩；而编写内核模块（Kernel Module）虽然速度快，但稍有指针越界就会直接导致整台操作系统内核崩溃（Kernel Panic）。

**eBPF (Extended Berkeley Packet Filter)** 彻底改写了这一局面。它宛如嵌入在 Linux 内核中的一个“安全沙箱虚拟机”，允许开发者在无需修改内核源码或重启服务器的前提下，以纳秒级开销动态运行受控的监控、网络过滤和安全审计程序。2024–2026 年，eBPF 已经成为云原生可观测性（Cilium、Falco 等）的核心技术基石。

---

## 适合人群

- 想要深入理解 Linux 操作系统底层运行细节的开发者与运维人员。
- 经常遇到系统偶发卡顿、文件被未知进程意外篡改却难以抓包取证的工程师。
- 听说过 eBPF、Cilium、BCC，希望从原理到动手快速入门的技术探索者。

## 学习目标

完成本章后，你应该能够：

- 解释为什么 eBPF 能在“绝对安全且不崩溃内核”的前提下实现高性能内核探查。
- 理解 eBPF 的核心生命周期流（编写源码 -> 字节码 -> 验证器 Verifier -> JIT 编译 -> 内核挂载点 Hook）。
- 辨析常见的内核钩子类型（`kprobe`、`kretprobe`、`tracepoint`、`XDP`、`uprobe`）。
- 熟练使用轻量 DSL 工具 **`bpftrace`**，用单行指令实时追踪系统调用、监控文件操作和绘制延迟直方图。

---

> [!IMPORTANT]
> **前置运行条件须知：**
> 1. **内核要求**：eBPF 需要现代 Linux 内核支持（推荐 Linux 5.4+；使用 `uname -r` 查看内核版本）。老旧架构（如 OpenVZ 虚拟化 VPS）由于缺少内核特权支持，无法运行 eBPF。
> 2. **独立工具**：本教程中使用的命令行工具 `bpftrace` **不是系统出厂自带工具**，必须先行通过包管理器安装（见下文安装小节），直接输入命令会提示 `command not found`。
> 3. **权限要求**：挂载探针需要 `root` 特权（`sudo`）或具备 `CAP_BPF` 内核能力。

## 先看架构与生命周期模型

```text
[用户态 (User Space)]
  用户编写的观测脚本 / C 语言 eBPF 程序
          ↓ (LLVM / Clang 编译)
  eBPF 机器字节码 (Bytecode)
          ↓ (调用 bpf() 系统调用载入内核)
-------------------------------------------------------
[内核态 (Kernel Space)]
   +-----------------------------------------------+
   | 1. 内核验证器 (Verifier)                      |
   |    - 检查死循环 (保证在有限步内必然终止)       |
   |    - 检查内存指针是否越界 (绝对禁止越界读取)    |
   |    - 检查未初始化变量                          |
   +-----------------------------------------------+
          ↓ (验证通过，若有风险直接在此处被拦截驳回)
   +-----------------------------------------------+
   | 2. JIT (Just-In-Time) 即时编译器              |
   |    - 将安全字节码转换为硬件机器指令 (x86/ARM)  |
   +-----------------------------------------------+
          ↓
   +-----------------------------------------------+
   | 3. 挂载到内核钩子 (Hook Points)               |
   |    [kprobe] [tracepoint] [XDP] [socket]       |
   +-----------------------------------------------+
          ↓ (事件触发执行，零拷贝记录数据)
   +-----------------------------------------------+
   | 4. BPF Maps (高性能键值对共享存储内存)          |
   +-----------------------------------------------+
          ↑ (用户态异步安全读取数据与统计报表)
```

### 验证器 (Verifier)：为什么 eBPF 不会让系统崩溃？

任何载入内核的 eBPF 字节码在执行前，必须通过内核 Verifier 的严格静态模拟分析：
1. **防止死循环**：所有循环分支必须能在有限步内收敛。
2. **指针安全与内存边界**：禁止随意解引用内核原始指针，必须通过专用的内核安全助手函数（Helper Functions）读取。
3. **指令数量上限**：防止单一探针过度霸占 CPU 算力。

## 常见挂载钩子 (Hook Points) 速查

| 钩子类型 | 作用位置 | 稳定性 | 典型应用场景 |
| :--- | :--- | :--- | :--- |
| **`tracepoint`** | 内核官方预先埋设的标准静态探针点 | **极高**（跨内核版本兼容好） | 统计系统调用频率、进程创建销毁监控 |
| **`kprobe`** | 任意内核函数的入口动态注入 | 随内核函数符号变动可能失效 | 探查未暴露标准埋点的内核深层私有函数 |
| **`kretprobe`** | 任意内核函数的退出返回处 | 随内核函数符号变动 | 测量特定内核操作执行耗时、获取函数返回值 |
| **`uprobe`** | 用户态进程（如 libc、Python 解释器） | 依赖用户态二进制符号表 | 追踪应用内部函数调用、SSL 明文解密分析 |
| **`XDP`** | 极早期的网卡驱动数据包接收层（在 sk_buff 分配前） | **极高** | 抗百 Gbps DDoS 攻击、线速负载均衡与丢包 |

## 用 bpftrace 快速体验内核洞察

`bpftrace` 是一种针对 Linux eBPF 的高级追踪语言，语法受 AWK 和 C 的启发，非常适合在终端以单行（One-liner）形式快速排错。

### 1. 安装 bpftrace

```bash
# Ubuntu / Debian
sudo apt update && sudo apt install -y bpftrace

# Fedora
sudo dnf install -y bpftrace
```

### 2. 实战案例一：谁在打开系统中的敏感文件？

排查恶意进程或偶发配置文件篡改，实时打印当前发生 `openat` 系统调用的进程名与对应文件路径：

```bash
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("PID %-6d [%s] 正在打开: %s\n", pid, comm, str(args.filename)); }'
```

*按 `Ctrl + C` 终止，终端会实时输出如：*
```text
PID 1420   [cron]   正在打开: /etc/crontab
PID 2588   [python] 正在打开: /app/config.json
PID 310    [systemd]正在打开: /proc/self/mountinfo
```

---

### 3. 实战案例二：统计全系统进程系统调用频次排行榜

```bash
sudo bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'
```

*运行几秒后按 `Ctrl + C`，bpftrace 会自动汇总并按调用次数从小到大打印直方图：*
```text
@[sshd]: 18
@[redis-server]: 142
@[node]: 320
@[python]: 1250
```

---

### 4. 实战案例三：磁盘 Block I/O 读取耗时分布直方图

测量系统实际磁盘读写延迟，观察是否存在偶发的“长尾阻塞（Tail Latency）”：

```bash
sudo bpftrace -e '
kprobe:vfs_read { @start[tid] = nsecs; }
kretprobe:vfs_read /@start[tid]/ {
    @latency_us = hist((nsecs - @start[tid]) / 1000);
    delete(@start[tid]);
}'
```

*输出结果示例（对数区间直方图展示微秒分布）：*
```text
@latency_us: 
[1]                  128 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@|
[2, 4)                45 |@@@@@@@@@@@@@                           |
[4, 8)                12 |@@@                                     |
[8, 16)                3 |@                                       |
[1024, 2048)           1 |                                        | (检测到一次毫秒级严重阻塞!)
```

## 生产级 eBPF 生态选型

当需要把 eBPF 探针做成长期运行的守护进程或服务时，通常使用更成熟的工业级框架：

- **BCC (BPF Compiler Collection)**：提供 Python / C++ 封装接口，内置数十个开箱即用的性能排查脚本（如 `execsnoop`, `opensnoop`）。
- **libbpf + CO-RE (Compile Once, Run Everywhere)**：现代官方主力推荐体系，配合 BTF（BPF Type Format）实现跨不同内核版本的二进制免编译通用分发。
- **Cilium**：Kubernetes 现代容器网络插件（CNI），使用 eBPF 替代性能低下的 iptables 实现高性能服务网格与负载均衡。
- **Falco**：云原生运行时安全工具，利用 eBPF 监控未授权特权调用与容器逃逸行为。

---

## 安全提醒与权限边界

1. **运行权限**：执行 eBPF 探针必须具备 `root` 权限或专门的 `CAP_BPF` / `CAP_PERFMON` 内核能力。
2. **性能开销考量**：虽然 eBPF 开销极低，但在 `vfs_read` 或每秒数百万次的高频函数上挂载带复杂字符串格式化（`printf`）的探针仍会产生可感知的 CPU 负载，建议排查完毕及时关闭终端。

## 少量自查

1. **eBPF 相比传统加载内核模块（Kernel Module）最大的安全优势是什么？**
   - *参考答案*：eBPF 必须经过内核静态验证器（Verifier）的安全性模拟校验，杜绝了死循环、非法野指针访问，因此即便探针逻辑存在缺陷，也绝不会导致操作系统整机 Crash。
2. **在观察文件打开时，为什么优先选用 `tracepoint:syscalls:sys_enter_openat` 而不是 `kprobe`？**
   - *参考答案*：`tracepoint` 是内核官方长期维护的标准接口，函数名与参数相对固定；而 `kprobe` 依赖特定内核版本的私有函数实现，内核升级时可能因函数改名而失效。
3. **BPF Maps 在系统体系中承担什么职责？**
   - *参考答案*：BPF Maps 是内核态 eBPF 程序与用户态管理进程之间进行异步、高性能、线程安全数据交互的共享键值存储区域。
