# 2.4 systemd 服务沙箱与凭据管理

把程序交给 systemd 管理，不只意味着“能开机启动”。systemd 还可以限制服务能看到哪些文件、设备和内核接口，以及用什么方式读取密钥。本章用渐进式方法给普通后台服务增加最小权限。

## 适合人群

- 已会用 `systemctl status` 和 `journalctl` 查看服务的新手。
- 正在 VPS 上部署自己编写的 API、定时任务或后台程序的人。
- 想减少服务被入侵后的影响范围，但还没有容器安全经验的人。

## 学习目标

完成本章后，你应该能够：

- 区分程序自身权限、Linux 用户权限和 systemd 沙箱限制。
- 用 `systemd-analyze security` 找到服务缺少的隔离设置。
- 通过 drop-in 覆盖文件渐进加固服务，而不是修改软件包自带的 unit。
- 用 `DynamicUser=` 和 `StateDirectory=` 管理服务身份与可写目录。
- 用 `LoadCredential=` 传递敏感文件，而不是把密钥直接写进环境变量。
- 在重启前验证配置，并在不兼容时找到具体失败原因。

## 先建立安全模型

假设一个网络服务出现了代码执行漏洞。如果它以 root 身份运行，并且能读写整个文件系统、访问设备和内核接口，攻击者得到的活动空间会很大。

systemd 加固的目标是缩小这个空间：

```text
应用自身的账号和权限
        +
普通 Linux 用户/组权限
        +
systemd 文件系统、设备、能力、命名空间限制
        +
防火墙、应用认证、更新和日志监控
```

systemd 沙箱只是其中一层。它不能替代安全更新、应用认证、防火墙或代码审计。

## 第一步：确认版本和原始配置

不同 Linux 发行版携带的 systemd 版本不同，支持的指令也可能不同。先检查：

```bash
systemd --version
systemctl cat demo-reader.service
systemctl show demo-reader.service -p FragmentPath -p DropInPaths
```

这里用 `demo-reader.service` 代表你自己的服务名。不要直接照搬，先替换成真实名称。

- `systemctl cat` 会显示主 unit 和已有 drop-in。
- `FragmentPath` 是主 unit 文件位置。
- `DropInPaths` 是管理员追加的覆盖文件。

如果某条指令不确定是否受当前系统支持，查本机手册最可靠：

```bash
man systemd.exec
man systemd.service
```

### 为什么不直接修改 `/usr/lib/systemd/system`

软件包升级可能覆盖这个目录中的 unit。管理员应使用：

```bash
sudo systemctl edit demo-reader.service
```

它通常会创建 `/etc/systemd/system/demo-reader.service.d/override.conf`。升级软件包时，覆盖文件仍会保留。

如果服务已经有覆盖文件，先阅读并备份其内容，不要覆盖其他管理员留下的配置。

## 第二步：先做一次安全审计

```bash
sudo systemd-analyze security --no-pager demo-reader.service
```

输出会列出各种限制是否启用，并给出 `0.0` 到 `10.0` 的暴露程度估算。数字越低，表示 systemd 能观察到的隔离通常越多。

这个分数是检查线索，不是漏洞扫描结果：

- 高分不等于服务已经存在漏洞。
- 低分不等于应用代码、认证和网络配置都安全。
- 工具只评估 systemd 自己提供的部分机制。
- 某些服务确实需要网络、设备或特定系统调用，不能为了分数盲目禁用。

保存加固前的输出，完成后再比较，重点看具体限制，而不是只看总分。

## 第三步：给普通后台服务添加基础限制

下面假设 `demo-reader`：

- 不需要 root。
- 需要访问网络。
- 只需要写入自己的状态目录。
- 不需要访问硬件设备、内核模块和用户主目录。

执行：

```bash
sudo systemctl edit demo-reader.service
```

添加：

```ini
[Service]
DynamicUser=yes
StateDirectory=demo-reader
RuntimeDirectory=demo-reader

NoNewPrivileges=yes
PrivateTmp=yes
PrivateDevices=yes
ProtectSystem=strict
ProtectHome=yes
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
ProtectClock=yes
RestrictSUIDSGID=yes
LockPersonality=yes

CapabilityBoundingSet=
AmbientCapabilities=
```

### 每组设置解决什么问题

| 设置 | 作用 | 常见影响 |
| :--- | :--- | :--- |
| `DynamicUser=yes` | 启动时分配临时用户，停止后释放 | 程序不能依赖固定 UID |
| `StateDirectory=` | 创建持久状态目录 `/var/lib/demo-reader` | 应用要把可写数据放到这里 |
| `RuntimeDirectory=` | 创建运行期目录 `/run/demo-reader` | 重启或开机后会重新创建 |
| `NoNewPrivileges=yes` | 禁止进程通过 `setuid` 等方式获得新权限 | 依赖提权工具的程序会失败 |
| `PrivateTmp=yes` | 给服务单独的临时目录视图 | 不能再与其他程序通过 `/tmp` 共享文件 |
| `PrivateDevices=yes` | 只暴露最基本的伪设备 | 摄像头、GPU、串口等设备不可用 |
| `ProtectSystem=strict` | 默认把系统文件树设为只读 | 未声明的写入路径会报只读错误 |
| `ProtectHome=yes` | 隐藏 `/home`、`/root`、`/run/user` | 不能读取用户目录中的配置和文件 |
| `ProtectKernel*=yes` | 限制修改内核参数、模块和控制组 | 管理或监控类程序可能不兼容 |
| `RestrictSUIDSGID=yes` | 禁止创建 setuid/setgid 文件 | 普通业务服务通常不受影响 |
| `CapabilityBoundingSet=` | 清空可获得的 Linux capabilities | 绑定低端口等操作可能需要例外 |

`DynamicUser=yes` 在较新的 systemd 中会隐含部分保护，但把关键意图写清楚，便于审查和跨机器比较。

### 服务需要写文件怎么办

不要因为一次 `Permission denied` 就取消 `ProtectSystem=strict`。先确定程序真正需要写到哪里。

优先使用 systemd 管理的目录：

```ini
[Service]
StateDirectory=demo-reader
CacheDirectory=demo-reader
LogsDirectory=demo-reader
RuntimeDirectory=demo-reader
```

对应路径通常是：

| 指令 | 常见路径 | 生命周期 |
| :--- | :--- | :--- |
| `StateDirectory=` | `/var/lib/demo-reader` | 持久保存 |
| `CacheDirectory=` | `/var/cache/demo-reader` | 可删除并重新生成 |
| `LogsDirectory=` | `/var/log/demo-reader` | 持久日志；也可直接用 journal |
| `RuntimeDirectory=` | `/run/demo-reader` | 运行期临时数据 |

如果软件的路径无法调整，再精确声明额外写入位置：

```ini
[Service]
ReadWritePaths=/srv/demo-reader/uploads
```

不要用 `ReadWritePaths=/`，那会基本抵消文件系统保护。

## 第四步：按真实需求增加限制

下面这些设置很有用，但更容易破坏兼容性。一次只增加一项，并在每次修改后测试。

| 场景 | 可考虑的设置 | 先确认什么 |
| :--- | :--- | :--- |
| 完全不需要网络 | `PrivateNetwork=yes` | 服务不监听端口，也不访问 DNS、数据库或 API |
| 只用常规网络套接字 | `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6` | 不需要 Netlink、原始套接字等协议族 |
| 不使用 JIT | `MemoryDenyWriteExecute=yes` | Java、浏览器、部分 ML/运行时可能需要可执行内存 |
| 不创建命名空间 | `RestrictNamespaces=yes` | 容器、沙箱和部分运行时可能依赖命名空间 |
| 只需常规系统调用 | `SystemCallFilter=@system-service` | 先在测试机观察，复杂程序可能被拦截 |

网络服务通常不能使用 `PrivateNetwork=yes`。需要绑定 80、443 等低端口时，也不要恢复全部 capabilities，可以只保留：

```ini
[Service]
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
AmbientCapabilities=CAP_NET_BIND_SERVICE
```

更好的架构是让反向代理监听公网低端口，应用只监听本机高端口。

## 第五步：不要把密钥直接写进 unit

下面这种写法很直观，但不适合敏感值：

```ini
[Service]
Environment=API_TOKEN=real-secret-value
```

unit 内容可能被其他用户或管理接口读取，环境变量还会传给子进程。更合适的方式是 systemd credentials。

先创建仅 root 可读的源文件：

```bash
sudo install -d -m 0700 /etc/demo-reader
sudo install -m 0600 /dev/null /etc/demo-reader/api-token
sudoedit /etc/demo-reader/api-token
```

然后在覆盖文件中增加：

```ini
[Service]
LoadCredential=api-token:/etc/demo-reader/api-token
```

服务启动时，systemd 会把凭据复制到该服务可读的只读目录，并设置 `$CREDENTIALS_DIRECTORY`。程序应读取：

```text
$CREDENTIALS_DIRECTORY/api-token
```

如果程序只能接收文件路径，可以让 systemd 展开路径：

```ini
[Service]
ExecStart=/usr/local/bin/demo-reader --token-file=${CREDENTIALS_DIRECTORY}/api-token
```

注意：

- `LoadCredential=` 改善了运行期传递方式，但源文件仍要使用严格权限保护。
- 修改源文件后要重启服务，新的凭据副本才会生效。
- 不要使用 `SetCredential=` 保存私钥或密码，因为 unit 通常可读。
- `LoadCredentialEncrypted=` 和 `systemd-creds` 可进一步保护磁盘上的凭据，但依赖系统版本、密钥或 TPM2，适合理解基础流程后再学习。

## 第六步：验证、重载和观察

先检查 unit 语法和引用：

```bash
unit_path=$(systemctl show demo-reader.service -p FragmentPath --value)
sudo systemd-analyze verify "$unit_path"
```

再让 systemd 重新读取配置：

```bash
sudo systemctl daemon-reload
sudo systemctl restart demo-reader.service
sudo systemctl status demo-reader.service --no-pager
sudo journalctl -u demo-reader.service -n 100 --no-pager
```

确认业务功能正常后，再重新审计：

```bash
sudo systemd-analyze security --no-pager demo-reader.service
```

### 远程服务器上的安全顺序

1. 不要第一次就拿 `ssh.service` 或 `sshd.service` 练习。
2. 保留第二个 SSH 会话，并确认云厂商控制台可以登录。
3. 一次只改一组限制。
4. 先 `verify`，再 `daemon-reload`，最后重启目标服务。
5. 重启后立刻检查状态、日志和真实业务请求。

`systemd-analyze verify` 能发现语法和部分依赖错误，但不能证明程序在沙箱里一定能正常工作，所以业务验证不能省略。

## 常见失败与定位

### `Read-only file system`

通常是 `ProtectSystem=strict` 生效，而程序仍在写未声明路径。查看日志，改用 `StateDirectory=`、`CacheDirectory=` 或精确的 `ReadWritePaths=`。

### `Permission denied`

依次检查：

```bash
systemctl show demo-reader.service -p User -p Group -p DynamicUser
systemctl show demo-reader.service -p StateDirectory -p ReadWritePaths
journalctl -u demo-reader.service -n 100 --no-pager
```

不要直接改成 root 或 `chmod 777`。先确认是普通文件权限、目录缺失，还是 systemd 沙箱拒绝。

### 无法监听端口

如果是 1024 以下的低端口，检查是否缺少 `CAP_NET_BIND_SERVICE`。如果所有网络都不可用，检查是否误用了 `PrivateNetwork=yes` 或过严的 `RestrictAddressFamilies=`。

### 程序启动后立即崩溃

暂时撤回最后新增的一项限制，重启并比较日志。最常见的高兼容性风险来自：

- `MemoryDenyWriteExecute=yes`
- `SystemCallFilter=`
- `RestrictNamespaces=yes`
- `PrivateNetwork=yes`
- 过窄的 `CapabilityBoundingSet=`

## 如何回滚

先查看当前覆盖文件：

```bash
systemctl cat demo-reader.service
```

用 `sudo systemctl edit demo-reader.service` 删除本轮新增的指令，然后执行：

```bash
sudo systemctl daemon-reload
sudo systemctl restart demo-reader.service
```

如果这个服务以前没有任何本地覆盖，也可以使用 `systemctl revert` 恢复供应商版本。但它会移除该 unit 的全部本地覆盖，不适合已有其他自定义配置的服务。

## 小练习

1. 对一个非关键服务运行 `systemd-analyze security`，找出三项未启用的保护。
2. 判断该服务真正需要写入、读取和联网的范围。
3. 只增加 `NoNewPrivileges=yes` 与 `PrivateTmp=yes`，验证服务和日志。
4. 再尝试 `ProtectSystem=strict` 配合 `StateDirectory=`，记录出现过的路径错误。

参考答案没有唯一组合。正确做法应能说明“为什么服务需要这项权限”，并有可重复的验证步骤。
