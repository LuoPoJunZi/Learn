# 2.6 systemd Timers：用现代方式替代传统 Cron 定时任务

在传统 Linux 运维中，定时执行备份、日志轮转或健康检查通常依赖 `crontab -e`。但 `cron` 存在几个长期痛点：任务失败时不容易集中查日志、服务器关机错过了窗口不会自动补跑、多台服务器同时整点触发容易造成“惊群”流量峰值，也难以对任务本身做权限沙箱限制。

在现代主流 Linux 发行版上，**systemd Timers** 已经成为推荐的定时任务方案。它把“要做什么（`.service`）”和“什么时候做（`.timer`）”拆成两个清晰单元，天然接入 `journalctl` 日志体系，并能直接复用 [2.4 systemd 服务沙箱与凭据管理](2.4-systemd-hardening.md) 的安全隔离能力。

---

## 适合人群

- 已经会用 `systemctl status` 和 `journalctl` 查看服务状态的新手。
- 写过 `crontab`，但经常因为环境变量缺失、日志无处查找而困惑的运维学习者。
- 希望在 VPS 上规范管理定时备份、证书检查或脚本巡检的维护者。

## 学习目标

完成本章后，你应该能够：

- 先检查当前系统是否运行在 `systemd` 环境下，避免在容器或非 systemd 发行版上误操作。
- 对比 `cron` 与 `systemd timers` 的核心差异。
- 编写成对的 `.service`（`Type=oneshot`）与 `.timer` 单元文件，并配置 `Persistent=true` 与 `RandomizedDelaySec=`。
- 使用 `systemd-analyze calendar` 校验时间表达式，用 `systemctl list-timers` 检查下一次触发时间。
- 在不需要时彻底停用并安全回滚清理练习单元。

---

> [!IMPORTANT]
> **前置环境检查（先确认再操作）：**
> `systemd timers` 仅适用于以 `systemd` 为 1 号进程（PID 1）的 Linux 系统（如 Ubuntu、Debian、Fedora、Rocky/RHEL）。在 Alpine Linux、WSL 未开启 systemd 模式或精简 Docker 容器中，`systemctl` 会报错 `System has not been booted with systemd as init system`。
> 请先运行：
> ```bash
> ps -p 1 -o comm=
> ```
> 只有当输出为 `systemd` 时，才继续执行本教程命令。

## systemd Timers vs 传统 Cron

| 对比维度 | 传统 Cron (`crontab`) | systemd Timers (`.timer` + `.service`) |
| :--- | :--- | :--- |
| **任务日志** | 需手动重定向 `>> /var/log/...` 或依赖本地邮件 | 自动汇入 `journald`，用 `journalctl -u 任务名` 一键按时间过滤 |
| **停机补跑** | 服务器关机错过时间点后直接跳过 | 设置 `Persistent=true` 后，开机自动补跑错过的一次任务 |
| **防并发与防惊群** | 容易出现上一次未结束又启动新实例；多机整点同时触发 | 同一 service 天然防重叠；支持 `RandomizedDelaySec=` 随机错峰 |
| **单独手动测试** | 往往需要把命令单独复制出来跑，环境变量还不一致 | 直接 `systemctl start demo.service` 即可用同一套环境手动试跑 |
| **安全沙箱** | 基本无隔离能力 | 可直接叠加 `DynamicUser=yes`、`ProtectSystem=strict` 等沙箱指令 |

## 第一步：先用工具验证时间表达式

在写 `.timer` 之前，强烈建议先用系统自带的 `systemd-analyze calendar` 校验 `OnCalendar` 写法，确认接下来几次触发时间完全符合预期：

```bash
# 查看“每天凌晨 03:15”接下来 5 次触发时间
systemd-analyze calendar --iterations=5 "*-*-* 03:15:00"

# 查看“每 10 分钟一次”
systemd-analyze calendar --iterations=5 "*:0/10"
```

如果表达式语法有误，该命令会立即报错，避免写进配置文件后静默失效。

---

## 第二步：编写一对 `.service` 与 `.timer`（用户级安全练习）

为了避免直接改动 `/etc/systemd/system/` 影响生产环境，下面演示在**用户级目录**（`~/.config/systemd/user/`）创建一个纯只读的健康检查练习任务，不需要 `root` 权限修改系统文件。

先创建目录：

```bash
mkdir -p ~/.config/systemd/user
```

### 1. 创建任务单元：`~/.config/systemd/user/demo-healthcheck.service`

```ini
[Unit]
Description=Demo read-only system uptime healthcheck

[Service]
Type=oneshot
ExecStart=/usr/bin/uptime
```

- `Type=oneshot` 表示这是一个执行完就退出的一次性任务，而不是常驻后台的守护进程。
- 命令尽量使用绝对路径（如 `/usr/bin/uptime`，可用 `command -v uptime` 确认本机实际路径）。

### 2. 创建定时器单元：`~/.config/systemd/user/demo-healthcheck.timer`

```ini
[Unit]
Description=Run demo healthcheck every 15 minutes

[Timer]
OnCalendar=*:0/15
Persistent=true
RandomizedDelaySec=2min

[Install]
WantedBy=timers.target
```

关键参数含义：
- `OnCalendar=*:0/15`：每小时的 `00`、`15`、`30`、`45` 分触发。
- `Persistent=true`：若机器在预定时间处于关机状态，下次开机后会补跑一次。
- `RandomizedDelaySec=2min`：在预定时间后额外增加 `0~2` 分钟随机延迟，避免多台机器同时访问同一外部接口造成拥堵。

## 第三步：校验、启用并观察运行日志

```bash
# 1. 重新加载用户级 systemd 配置
systemctl --user daemon-reload

# 2. 先手动试跑一次 .service，确认脚本本身不报错
systemctl --user start demo-healthcheck.service
journalctl --user -u demo-healthcheck.service -n 10 --no-pager

# 3. 启用并启动定时器（注意启用的是 .timer，不是 .service）
systemctl --user enable --now demo-healthcheck.timer

# 4. 查看所有已激活定时器及下一次触发倒计时
systemctl --user list-timers --all
```

> [!NOTE]
> 如果是系统级生产定时任务（放在 `/etc/systemd/system/` 下），去掉 `--user` 并在命令前加 `sudo` 即可。用户级定时器在用户退出 SSH 登录默认会停止；若希望注销后仍持续运行，需要管理员开启 linger：`sudo loginctl enable-linger "$USER"`。

---

## 常见故障排查

### 1. 启用后任务一直没触发
- **排查**：检查你执行的是不是 `enable demo-healthcheck.timer`（常见失误是误把 `.service` 设为开机自启，却忘了启动 `.timer`）。运行 `systemctl --user list-timers` 确认目标是否在列表中。

### 2. 报错 `status=203/EXEC`
- **原因**：`ExecStart=` 指定的二进制或脚本路径不存在，或者脚本缺少可执行权限（`chmod +x`）及首行 Shebang（如 `#!/usr/bin/env bash`）。
- **解决**：先用 `command -v 命令名` 核对真实绝对路径。

## 如何安全回滚与清理

练习完成后，按以下步骤彻底停用并删除演示文件，保持系统整洁：

```bash
systemctl --user disable --now demo-healthcheck.timer
rm -f ~/.config/systemd/user/demo-healthcheck.timer ~/.config/systemd/user/demo-healthcheck.service
systemctl --user daemon-reload
systemctl --user list-timers --all
```

## 少量自查

1. **为什么定时任务对应的 `.service` 通常把 `Type` 设为 `oneshot` 而不是 `simple`？**
   - *参考答案*：`oneshot` 会等待脚本完全执行结束才算本次激活完成，便于 systemd 准确记录退出码并防止上一次还没跑完就重叠触发。
2. **`Persistent=true` 解决什么问题？**
   - *参考答案*：如果服务器因维护或重启错过了预定的触发时间点，systemd 会在开机后自动补跑一次，防止关键备份或清理任务被静默漏掉。
3. **为什么建议在多台服务器上配置 `RandomizedDelaySec=`？**
   - *参考答案*：把整点并发请求打散到一段随机窗口内，避免所有服务器在同一秒冲击数据库、备份存储或外部 API（惊群效应）。
