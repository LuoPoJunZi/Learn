# 混合检索与 RRF：把多路排名融合起来

## 适合人群与学习目标

适合已经理解 [迷你 RAG 检索](examples/mini_rag_retrieval.py) 中“查询 → 检索 → 上下文”的学习者。学完应能解释关键词与语义检索的互补关系、手算 RRF，并使用标注集合做最小质量检查。

资料核验：**2026-10-30**。RRF 是已有的排序融合算法，不是 2026 年新发明；本页依据当前官方工程文档，补充现代 RAG 中常用的混合检索思路。

## 为什么一个检索器可能不够

- 搜索错误码、API 名或型号时，关键词精确匹配很重要。
- 搜索“怎样让程序换电脑也能跑”时，文档可能写的是“依赖锁定与环境复现”，语义检索可能更有帮助。
- 向量相似度不代表真实性，关键词命中也不代表文章真的能解决问题。

混合检索让不同方法各自返回候选，再融合排名。Azure AI Search 的官方混合检索文档提供了“全文检索 + 向量检索 + RRF”的实际产品例子；本仓库不需要 Azure 账号，也不调用云服务。

## 三个阶段不要混淆

| 阶段 | 输入输出 | 作用 |
| :--- | :--- | :--- |
| 召回 | 查询 → 每路候选列表 | 尽量找到可能相关的文档 |
| 排名融合 | 多个有序列表 → 一个列表 | 综合各检索器提供的位次信息 |
| 重排序 | 候选与查询 → 新顺序 | 更细致地评估相关性，例如使用专用 reranker |

RRF 是排名融合，不是向量模型，也不是对文档逐对推理的交叉编码重排序器。最后的答案生成又是另一个步骤，本例不生成回答。

## 公式：只比较位次，不直接相加原始分数

对文档 d，融合分数为：

```text
score(d) = 各列表中 weight / (k + rank(d)) 的和
```

- `rank` 从 **1** 开始；某列表没有该文档，则该列表贡献为 0。
- `k` 是平滑常数，示例默认 60；不是向量检索“取多少邻居”的 top-k。
- `weight` 表示该检索器的贡献权重，默认 1；本例权重 0 的检索器不引入候选。

例如两路结果为 `[a, b]` 与 `[b, c]`：

```text
a: 1 / 61
b: 1 / 62 + 1 / 61
c: 1 / 62
```

b 两次排在前面，最终超过只出现一次的 a。关键词 BM25 和向量余弦分数常处在不同量纲，直接相加会被数值尺度误导；RRF 避开原始分数尺度问题，但也丢弃了原始分数差距的信息。

## 运行离线案例

要求 Python 3.10+ 标准库，无模型下载、无数据库、无文件写入：

```powershell
python "Python/Modern AI/examples/reciprocal_rank_fusion.py"
python -m unittest discover -s scripts/tests -p "test_retrieval_and_protocol.py" -v
```

源码：[reciprocal_rank_fusion.py](examples/reciprocal_rank_fusion.py)。输入是**手工编写的两路结果列表**，其中所谓 semantic 列表只是固定教学数据，不代表代码运行了 Embedding 或语义检索。

观察重点：重复出现的文档分数累加；未出现在某一路的文档不获得那一路分数；同分时按文档 ID 排序，保证输出可复现。

## 如何给不同列表对齐文档

融合依据的是统一文档 ID，不是文档标题。相同资料若使用不同 ID，就不会累加；不同资料若错误复用 ID，就会被错误合并。

本实现拒绝**同一路列表内**重复 ID，避免重复计分。跨列表出现相同 ID 则恰恰是融合需要的正常情况。

真实系统还应统一版本与切片粒度：一个列表排整篇文章、另一个列表排段落时，应先决定按文章融合还是按 chunk 融合，不能只看名称相似就合并。

## 用 Recall@K 做最小检查

示例提供：

```text
Recall@K = 前 K 项中命中的不同相关文档数量 / 所有已标注相关文档数量
```

相关集合由人预先标注，不是把检索结果自己定义为相关。重复 ID 只算一次；没有已标注相关文档时，本例直接报错，避免悄悄把“无法评估”记成 0 或 1。

案例中单路与融合的 Recall@2 都是 2/3，**没有证明融合更好**。这是刻意保留的教学结果：融合算法有用不等于任何查询都改善。实际评估要增加真实查询，并按目标考虑 Precision@K、MRR、nDCG、延迟和成本。

## 典型场景与常见错误

- **适合**：企业文档中同时包含自然语言问题、错误码、专业名词和版本号。
- **不应融合后才想起权限**：各路候选在返回给用户或模型前必须满足用户访问权限；融合分数不能绕过 ACL。
- **不断增加检索器一定更好**：高度重复的检索器会重复投票，改变权重，未必增加有效信息。
- **不断增加候选一定更好**：可能增加噪声、排序开销和上下文成本，应在真实标注集上比较。
- **RRF 分数是置信度**：不是概率，不可把 0.03 显示成“3% 正确率”。
- **上下文命中了就不会幻觉**：仍需保留引用、版本过滤、答案核对；检索内容本身也可能包含错误或提示注入。

## 完成检查与下一步

能手算三篇文档的贡献、说清 `k` 与候选数量的区别、解释为什么玩具指标没提升，即完成最小闭环。返回 [现有 TF-IDF RAG](examples/mini_rag_retrieval.py) 看召回过程，或学 [MCP 工具消息](MCP_TOOLS_GUIDE.md) 理解如何把检索能力包装成受控工具。
