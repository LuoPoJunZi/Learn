# Agent 评测入门：答案正确，不等于任务完成

## 适合人群与学习目标

适合已理解 [Agent 工具调用](examples/ai_agent_tool_calling.py)、[MCP 工具消息](MCP_TOOLS_GUIDE.md) 的学习者。目标是为 Agent 设计可重复的最小评测，区分答案正确、工具成功、过程合规和运行成本，避免凭一段成功演示判断系统可靠。

来源核验：**2026-11-10**。参考 Hugging Face Agents Course 的可观测性与评测单元；评测本身是成熟工程实践，不是新发明的算法。本页先用纯标准库建立概念，不安装追踪平台、不连接在线模型、不上传日志。

## 一、为什么不能只检查最后一句话

假设任务要求“查找某篇指南并给出其 ID”。Agent 的搜索调用失败了，但碰巧猜中了 ID。如果只比较答案，就会记录为成功；实际却没有证明工具链正常。

另一个例子是付款或写文件：用户不仅关心最终文字，还关心有没有重复操作、有没有超过授权范围。**权限控制必须在执行前实施，评测不能事后替代授权。**

本例将评测拆成几层：

| 维度 | 本例判断方式 | 能说明什么 |
| :--- | :--- | :--- |
| 答案精确匹配 | 去除两端空白后与标注答案一致，且没有运行级错误 | 固定格式任务是否答对 |
| 必要工具使用 | 每个要求的工具至少成功调用一次 | 是否使用了要求的数据或计算来源 |
| 工具错误 | 失败事件数 / 工具事件总数 | 已观察到的工具调用失败比例 |
| 调用预算 | 调用次数不超过用例限制 | 是否超出教学用的调用上限 |
| 严格任务成功 | 答案正确、必要工具成功、所有工具调用成功、未超预算 | 本例人为约定的完整通过条件 |

“严格任务成功”故意不把重试后恢复的失败忽略掉。真实产品可允许可恢复失败，但应明确策略，另行记录重试率，而不是悄悄改变指标定义。

## 二、先冻结用例，再比较版本

每条用例包含 `case_id`、`expected`、`required_tools` 和 `max_calls`。每条运行记录包含输出、工具事件、延迟和可选错误类别。

本例用三条固定用例：算术、检索、无需工具的拒绝任务。baseline 与 candidate 使用同一组标注；candidate 只修改其中一条工具事件的成功状态。**它们都是合成记录，不是真实 Agent 运行日志。**

生产中至少分开：

- 开发集：可以查看失败并调整提示词或代码。
- 保留测试集：不拿它反复调参，比较版本时才使用。
- 线上监控：反映真实流量，但不应把私人请求直接加入公开测试集。

## 三、运行最小评测台

源码：[agent_evaluation.py](examples/agent_evaluation.py)。要求 Python 3.10+，无依赖、无网络、无文件写入：

```powershell
python "Python/Modern AI/examples/agent_evaluation.py"
python -m unittest discover -s scripts/tests -p "test_learning_workflows.py" -v
```

第二条命令还包含迁移与可选 DuckDB 测试；没装 DuckDB 时，其三项测试明确显示跳过，Agent 测试照常运行。

预期核心输出：

| 指标 | baseline | candidate |
| :--- | :--- | :--- |
| 答案精确匹配率 | 100% | 100% |
| 严格任务成功率 | 2/3 | 100% |
| 工具调用总数 | 2 | 2 |
| 失败工具调用数 | 1 | 0 |
| 工具错误率 | 50% | 0% |
| 平均合成延迟 | 15 ms | 约 17.67 ms |

这个结果只验证计分逻辑：候选版本的过程更符合规则，但合成延迟更高。**不能据此宣称真实模型更可靠或更快。**

## 四、评测器为什么拒绝缺失和重复记录

常见错误是只统计完成的请求，把超时或崩溃的样本丢掉，导致成功率虚高。

本实现要求用例 ID 与运行 ID 一一对应。缺失、重复或多余的记录会报错；真实系统应为超时样本保存一条 `error="timeout"` 运行记录，而不是从分母删除。没有用例时同样报错，不返回“100% 成功”。

评测入口还验证实际字段类型：工具 `ok` 必须是布尔值，字符串 `"false"` 不被当作成功；ID 和工具名非空，答案为字符串，延迟必须是有限的非负数（教学保护上限为 1e15 毫秒），错误字段只能为 None 或非空错误类别。Python 类型标注不会替你做这些检查。

无工具调用时工具错误率约定为 0，同时保留 `tool_calls=0`，表示“没有可观察调用”，不等于工具已被充分验证。

## 五、最小追踪该记录什么

推荐记录任务 ID、工具名称、开始/结束时间、成功/失败与稳定错误类别。先确定字段与脱敏规则，再选平台。

本例不保存原始 prompt、工具参数、Token 或完整返回内容。不要把 API 密钥、客户文档、邮箱地址原样发往观测平台。真实系统可以通过 trace ID 关联步骤，通过 span 表示一次调用，再使用 OpenTelemetry 或合适的平台采集。

本例的 `latency_ms` 是固定数据。真正测耗时应使用单调计时器（如 `time.perf_counter`），明确是端到端延迟还是单次工具延迟，并考虑冷启动与重试。不要把“计时超过上限”当成已经实现了强制取消。

## 六、精确匹配、规则裁判与模型裁判怎么选

- **精确匹配**：适合 ID、短标签和标准答案。不会自动处理同义表达、单位换算和开放式解释。
- **规则校验**：适合 JSON 字段、引用是否存在、数值容差等结构约束。
- **人工评审**：适合重要、开放式或安全相关任务，需要清楚的评分标准。
- **LLM-as-a-judge**：适合辅助评估大规模开放式回答，但有偏差、成本、隐私和提示注入风险，不能直接当客观真值。

本例只做精确匹配与固定过程规则，不调用模型裁判。先用确定性测试抓住明显回归，再考虑复杂裁判。

## 常见错误与安全边界

- **选几条最容易成功的题做演示**：应按真实任务类别覆盖正常、无权限、错误、超时和缺资料场景。
- **只看平均数**：真实系统还需看延迟分位数、失败类别及样本量，本例三题不适合统计推断。
- **模型猜中也算工具成功**：本例分别计分；但单靠事件名称也无法证明真的查了可信来源，生产需验证可追溯证据。
- **把生成式 Agent 的随机性忽略掉**：固定模型、配置、工具版本和数据快照，多次运行并报告波动。
- **让评测自动执行危险任务**：用沙箱或离线替身，不对真实邮箱、支付系统或用户目录进行回归试验。

## 完成检查与下一步

能解释“答案 100% 正确但任务通过率只有 2/3”的原因、为失败保留记录、说明日志脱敏字段，即完成最小闭环。对照 [RRF 教程](HYBRID_RETRIEVAL_GUIDE.md) 区分检索指标和最终任务指标；再回看 [MCP 教程](MCP_TOOLS_GUIDE.md) 的权限与错误边界。
