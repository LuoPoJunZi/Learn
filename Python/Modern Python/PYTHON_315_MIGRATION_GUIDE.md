# Python 3.15 新特性与旧脚本迁移

## 适合人群与学习目标

适合已经会运行 Python、使用虚拟环境，并维护自动化脚本的初学者。目标不是一次记住所有语法，而是理解新版本改变了什么、哪些变化可能影响旧脚本，以及如何验证和回退。

官方来源核验：**2026-11-10**。Python 3.15 的 What's New 记载该版本于 2026-10-09 发布；新特性的精确行为以对应版本的语言和库参考为准。本仓库保留 [Python 3.14 特性导读](../../docs/CURRENT_CODE_TUTORIALS.md)，不把所有旧示例的最低版本改为 3.15。

**验证边界**：本轮可用解释器为 Python 3.13，不能据此声称已实测 3.15。下面的迁移检查脚本兼容 Python 3.10+；标明 3.15 的片段需要读者在独立 3.15 环境中运行。

## 一、先分清三个版本

| 名称 | 如何确认 | 为什么重要 |
| :--- | :--- | :--- |
| 终端实际解释器 | `python --version` | PATH 中可能有多份 Python |
| 编辑器解释器 | VS Code 的 Python 解释器选择 | 编辑器与终端可能不同 |
| 项目最低支持版本 | `pyproject.toml` 的 `requires-python` | 本机能跑不代表所有用户能跑 |

先运行只读检查脚本，不会修改系统设置、下载解释器或写文件：

```powershell
python "Python/Modern Python/migration_checks.py"
```

它显示解释器路径、UTF-8 模式、默认文本编码和相关内置类型是否存在，并演示“省略参数”与 `None` 的区别。类型不存在时会显示 `False`，不是安装失败；它也不是完整的 3.15 兼容性认证。

## 二、默认 UTF-8：新默认不等于旧文件自动转换

3.15 默认使用 UTF-8 模式。对 Windows 上历史遗留的 GBK、CP936 等文本，原来依赖本地默认编码的代码可能不再按预期读取。

应把“文件是什么编码”写清，而不是依赖机器设置：

```python
from pathlib import Path

# 下面是用法片段；先准备该文件，不要直接指向重要数据。
text = Path("notes.txt").read_text(encoding="utf-8")
```

若来源文件确定是 GBK，则明确指定 `encoding="gbk"`；不能根据乱码随便猜。报 `UnicodeDecodeError` 时先确认来源编码，不要立即使用 `errors="ignore"` 丢掉字符，也不要批量覆盖原文件。

排查流程：

1. 保留原文件和备份，选一份复制件做测试。
2. 确认生成软件和编码；必要时用十六进制查看器核对。
3. 使用明确编码读取，并检查中文、特殊符号和行数。
4. 需要转码时写入另一个新文件，复核后再由用户决定是否替换。

即使使用新默认，仓库代码仍推荐显式写 UTF-8，方便跨版本阅读与维护。

## 三、sentinel：省略参数与主动清空不是一回事

场景：更新昵称。没传参数表示“不修改”，传入 `None` 表示“清空昵称”，传入字符串表示“设置昵称”。如果默认参数直接使用 `None`，前两种意图就混在一起。

兼容旧版本的最小写法如下，完整实现见 [migration_checks.py](migration_checks.py)：

```python
MISSING = object()


def describe_update(value=MISSING):
    if value is MISSING:
        return "keep current value"
    if value is None:
        return "clear current value"
    return f"set value: {value}"
```

**Python 3.15 专属片段**可使用内置 sentinel 表达独立哨兵值：

```python
MISSING = sentinel("MISSING")


def update_nickname(value=MISSING):
    if value is MISSING:
        return "不修改"
    if value is None:
        return "清空昵称"
    return f"设置为 {value}"
```

用 `is` 检查该哨兵的身份；不要用 `if not value`，否则空字符串、0、False 和 None 会被混淆。不要为了使用新内置类型就删除所有旧版本兼容逻辑，也不要把进程内哨兵直接当成 JSON 通信协议字段。

## 四、frozendict：不可修改的映射不等于深度冻结

3.15 新增 `frozendict` 内置类型，值得理解的是可变配置与不可变配置的设计区别。它限制映射条目的修改，不应推断其内部所有嵌套对象都自动变为不可变，也不要假定它能直接替代所有 dict 用法。

迁移前先找这些操作：添加键、删除键、就地更新，以及修改配置中的嵌套列表。需要持续更新的状态应继续使用可变结构；需要明确配置快照时再考虑不可变映射，并按官方类型文档核对可哈希条件和方法。

本教程不将项目配置批量改写为新类型，避免抬高整仓库运行门槛。

## 五、惰性导入：推迟启动成本，也可能推迟错误

3.15 引入显式惰性导入能力。适用的思考场景是大型命令行应用：某个子命令才需要的重型依赖，不一定要在所有启动路径立即加载。

不能只看启动更快，还要检查：

- 模块导入时执行的注册、日志初始化或插件加载是否仍按预期发生。
- 缺失依赖异常是否被延迟到用户实际执行功能时才暴露。
- 冷启动、第一次调用和后续调用是否分别测量。

初学者先识别导入副作用，再按官方语言参考学习 3.15 语法。不要把导入时自动执行文件操作或网络请求当作值得保留的设计；也不要在需要兼容旧解释器的同一源文件中直接放新语法，然后以为版本判断能阻止解析失败。

## 六、按顺序做迁移，而不是覆盖系统 Python

1. 在工作分支保留当前代码、旧解释器和依赖记录。
2. 根据 [环境指南](../ENVIRONMENT_GUIDE.md) 独立安装目标版本；确认依赖支持目标版本和操作系统。
3. 用目标解释器创建一个新的虚拟环境，不复用旧 `.venv`。
4. 安装项目声明的依赖，运行单元测试和小样本脚本，不对真实目录执行批量修改。
5. 重点复核编码、导入副作用、第三方扩展和打包行为。
6. 若项目仍承诺支持旧版本，旧版本与 3.15 都要通过；确认后才调整最低版本声明。

Windows 已安装 Python Launcher 和 3.15 时，可手动执行：

```powershell
py -3.15 --version
py -3.15 -m venv .venv315
.\.venv315\Scripts\python.exe -m pip --version
```

这些命令会在当前目录创建环境。安装依赖可能联网，应在独立练习项目中执行。Linux/macOS 按实际安装的解释器路径创建环境，不照搬 Windows 路径。

回退时切回旧解释器与旧环境，撤销尚未确认的新特性代码；不通过修改原始数据来“适配”新解释器。

## 常见问题与完成检查

- **装了新版本，终端还是 3.13？** 检查 `sys.executable` 与编辑器解释器，不先卸载旧版本。
- **新特性能放进旧版函数的 if 分支里吗？** 新语法仍会被旧解释器解析；单独模块、明确版本门槛更可靠。
- **升级后一定更快吗？** 不保证，应以真实工作负载测量，区分初始化和稳定运行。
- **能用一次测试宣称全部兼容吗？** 不能；需要覆盖数据、依赖、操作系统和关键业务路径。

完成时应能解释编码风险、正确区分省略/None/0，并保留可用的旧环境和回退路径。
